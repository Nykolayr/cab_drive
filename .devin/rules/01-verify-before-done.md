# Verify-before-done

## Суть

Агент **сам** доводит задачу до проверяемого результата. «Код написан / задеплоено» ≠ «работает».  
Заказчику и пользователю **нельзя** писать «всё ок / починили / работает», пока нет факта проверки.

## Статусы (использовать явно)

| Статус | Когда можно сказать |
|--------|---------------------|
| **задеплоено** | код на сервере/в ветке, проверка ещё не сделана |
| **проверено мной** | smoke / логи / API / analyze / тесты прошли со стороны агента |
| **нужна твоя проверка** | нужен телефон / UI / OTP — агент сделал тест и ждёт «да/нет» |
| **можно заказчику** | есть факт проверки; дыры названы явно |

Без **проверено мной** или **можно заказчику** — не закрывать задачу формулировкой «работает».

## Что обязан сделать агент

1. После фикса/деплоя — **максимально возможный smoke** (терминал, API, SQL, health, логи, `flutter analyze`, тесты по проекту).
2. Если без устройства нельзя (push на экран, OTP, жест в UI) — **сам инициировать** тест и явно попросить подтверждение.
3. В конце ответа — короткий блок:
   - что проверил и результат;
   - что осталось на пользователе (если есть);
   - чего **не** проверял (если есть).
4. Блокер («нет токена», «нет доступа») — писать прямо, не маскировать «должно работать».

## Проверка актуальности (особенно для сторов/UI/API/CLI)

- Перед советом по App Store Connect, Google Play, RuStore, Xcode, Flutter и т.п. — **сверить актуальность** с официальной документацией или текущим UI пользователя.
- Если пользователь прислал скрин — опираться **на него**, а не на устаревшую схему «как обычно».
- Процедуры описывать **пошагово**: куда кликнуть, что выбрать, что будет дальше.

## Запрещено

- Обещать заказчику или пользователю рабочий результат без smoke/факта.
- Останавливаться на «хук есть / сервис active» без проверки эффекта.
- Путать **задеплоено** с **проверено**.
- «Должно работать» / «перезапусти и проверь» **без** своей проверки в этом же turn.
